# Design Pattern Justification (Requirement C8)

Every design pattern in FlagShip solves a concrete functional or quality requirement. No patterns are added speculatively.

| # | Pattern | Problem Solved | Requirement Supported | Participating Classes (Java & TypeScript) | Why Selected | Alternative Rejected |
|---|---------|----------------|-----------------------|-------------------------------------------|--------------|----------------------|
| 1 | **Strategy** | Extensible evaluation of 8 heterogeneous targeting operators (`SEMVER_GREATER_THAN`, `REGEX`, `DATE_BEFORE`, etc.) and pluggable deterministic rollout hashing. | FR2, FR3, QA4 | `FlagEvaluationEngine.OperatorStrategy`, `MurmurHash3` (`FlagEvaluationEngine.java`, `src/shared/engine.ts`) | Eliminates brittle switch/if-else chains and allows new operators to be registered without modifying core traversal logic. | Monolithic `if/else` method inside `FlagService`, which violates Open/Closed Principle and is harder to unit test in isolation. |
| 2 | **Composite** | Representing arbitrarily nested `AND` / `OR` targeting rule trees containing leaf conditions and reusable segment references. | FR2 | `RuleNode`, `RuleGroupNode`, `ConditionLeafNode`, `SegmentRefNode` (`FlagModels.java`, `src/shared/engine.ts`) | Uniform tree interface allows infinite nesting of condition groups using the exact same serialization and evaluation API. | Flat list of conditions with single global `AND`/`OR` flag, which cannot express `(plan=pro AND (country=US OR beta=true))`. |
| 3 | **Visitor** | Decoupling rule-tree traversal and evaluation (and future explanation/validation passes) from immutable rule AST data records. | FR2 | `RuleEvaluatorVisitor`, `RuleVisitor<T>` (`FlagEvaluationEngine.java`, `src/shared/engine.ts`) | Java 21 `sealed interface` + Visitor keeps `RuleNode` data records pure and framework-free while isolating cycle detection (`visitedSegments`). | Putting `evaluate(ctx)` directly inside JSON DTO records, which mixes domain evaluation state into serialization models. |
| 4 | **Chain of Responsibility** | Enforcing strict deterministic precedence: `Kill Switch -> Individual Targets -> Segment Rules -> Percentage Rollout -> Default`. | FR2, QA1 | `KillSwitchHandler`, `IndividualTargetHandler`, `SegmentRuleHandler`, `PercentageRolloutHandler`, `DefaultVariationHandler` (`src/shared/engine.ts`) | Makes the 5-stage precedence order explicit, self-documenting, and short-circuiting (e.g., Kill Switch halts evaluation in < 1 µs). | Single deeply nested evaluation function where precedence bugs can easily occur during maintenance. |
| 5 | **Observer** | Pushing configuration changes, kill switches, and approved rollouts immediately to all connected SDK instances. | FR5, QA3 | `SseStreamService` / `SseUpdateBus`, connected SSE subscribers (`SseStreamService.java`, `server/app.ts`) | Decouples write operations (`FlagController`, `ApprovalService`) from transport fan-out across N live SSE connections. | Tight polling loops every 1 second from every SDK pod, which wastes server CPU and misses sub-second kill-switch propagation. |
| 6 | **Proxy / Decorator** | Wrapping raw flag evaluation with in-memory snapshot caching, local disk persistence fallback, exposure buffering, and Micrometer timing. | FR4, FR6, QA1, QA2 | `DefaultFlagShipClient` wrapping `FlagEvaluationEngine` + `SnapshotStore` + `MeterRegistry` | Guarantees business code calls `flagShip.isEnabled(...)` with zero network I/O, zero uncaught exceptions, and built-in metrics. | Direct HTTP calls per `isEnabled()` check, which adds >10ms network latency and crashes business logic during server outages. |
| 7 | **Command** | Capturing immutable configuration snapshots per change so production releases can be previewed, audited, and deterministically rolled back. | FR7 | `flag_versions`, `change_requests`, `ApprovalService`, rollback endpoint (`server/app.ts`) | Treats every flag mutation as an explicit, reversible state transition with author, reason, and before/after snapshot. | Overwriting database columns in-place without version snapshots, making safe rollback impossible. |
| 8 | **Builder** | Ergonomic construction of immutable `EvaluationContext` objects with optional typed user attributes (`plan`, `appVersion`, `region`). | FR2, FR4, QA5 | `EvaluationContext.Builder` (`EvaluationContext.java`), `EvaluationContextBuilder` (`src/shared/engine.ts`) | Prevents telescoping constructors and keeps SDK call sites fluent and readable for developers adopting the starter in < 15 minutes. | Mutable `HashMap` passed directly to `evaluate()`, risking accidental mutation across concurrent evaluations. |
